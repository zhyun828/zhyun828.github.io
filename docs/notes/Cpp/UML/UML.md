## 1. 为什么先建模，再写 C++

### 1.1 模型不是现实的复制品

想象你要做一个取款机。直接写 `main()` 很容易，但你马上要决定：谁检查账户？谁操作出钞器？余额不足怎么办？跨银行交易发给谁？如果这些问题没有分清，写出的程序可能能运行，却与需求不一致。

模型（Model；法语 Modèle）是为了回答某个问题而保留现实的重要特征、舍去无关细节的抽象。地铁图保留站点与换乘关系，不保留每棵树；取款系统模型保留账户、交易和设备责任，不需要描述机箱颜色。模型必须有目的、边界和抽象层次。它减少复杂性，也能用于推演行为、检查规则和生成测试场景。不是每张 UML 图都能执行；可执行建模还需要具体行为、约束及工具支持。

统一建模语言（Unified Modeling Language，UML；法语 Langage de modélisation unifié）规定模型元素与图形表示。它让人和工具用一致的词汇表达结构及行为，可描述软件，也可描述包含人员、设备和流程的系统。它是**语言**，不规定团队必须按哪种开发方法工作，也不会自动决定怎样实现模型。C++ 是编程语言，负责把模型变成可执行行为。同一 UML 关联可以通过引用、指针、标识符或查询实现，具体选择属于实现设计。

课程强调三个收益：规范化使术语更精确、模型更稳定并便于工具处理；图形提供团队沟通的共同语言；抽象使复杂系统更容易分析。限制同样重要：漂亮的图不等于正确需求，箭头画得标准也不保证职责合理。

### 1.2 软件设计中必要的基础

第一份课件 p7–23 把复杂性分为业务范围与约束、互相连接的子系统、开发协作三个来源。对 UML 来说，直接的办法是划边界、分责任、约定接口。所谓“最底层组件”取决于当前问题：研究银行间路由时可以把一家银行看作一个节点，研究余额更新时又要展开账户与交易。

软件质量（Software Quality；Qualité du logiciel）不只有结果正确。外部质量包括效率、可靠性、健壮性、可移植性与满足需求；内部质量包括可读性、架构清晰、可验证性、数据与处理职责的合理组织。维护包括纠错维护与随需求变化的演进维护。扩展性、可修改性、复用性、兼容性和可维护性，是选择对象边界时应考虑的目标。例如把成绩查询规则与数据库地址写在一个类里，会使查询需求变化和存储变化影响同一处。

分析（Analysis；Analyse）回答“系统必须做什么”；设计（Design；Conception）回答“由哪些元素合作完成”；实现（Implementation；Implémentation）把设计落到语言与运行环境。需求规格、总体架构、详细类接口、代码不是互相替代的产物。课件 V 形图的相关含义是：需求可对应验收场景，总体设计可对应集成检查，详细接口可对应单元检查。这里不展开项目管理课程。

黑箱（Black Box；Boîte noire）只看输入、输出和服务契约；白箱（White Box；Boîte blanche）看内部机制。用例是系统黑箱视角，类图和内部时序通常是白箱视角。例如 PASS 输入姓名与课程名，输出成绩列表，这是黑箱；内部先由姓名查 ID、再用 ID 查成绩，是白箱。

模块（Module）是具有明确责任与边界的设计单位，可以是函数、类、一组文件或组件。把代码拆成文件不自动产生低耦合。组件（Component；Composant）把可替换的服务及所需接口封装成一个单元。课件的“编译好的软件积木”是实现层例子，UML 也能在逻辑层建模组件。公开接口告诉别人能请求什么，私有部分隐藏表示和算法；C++ `private` 提供语言访问控制，不能当作进程隔离或内存安全保证。

### 1.3 从分解问题走向对象责任

自顶向下（Top-down；Analyse descendante）从整体目标分解子目标，要求子目标共同覆盖原问题。自底向上（Bottom-up；Conception ascendante）从已有能力或具体场景归纳与组合整体方案。二者互补。例如课程“找列表最大值”的分解树分为初始化、遍历、比较与保存；比较器可以复用，而控制遍历的责任在上层。对象方法内部仍要执行算法，面向对象不消除算法设计。

面向对象设计（Object-oriented Design，OOD；Conception orientée objet，COO）安排对象职责；面向对象编程（Object-oriented Programming，OOP；Programmation orientée objet，POO）用代码实现对象协作；支持对象的语言（Langage par objets，LPO）只是工具。使用 C++ 类语法不证明你做了合理对象设计。命令式描述执行步骤，声明式描述目标，事件式描述对事件的响应，过程式以过程组织处理，函数式以函数组合组织计算，组件式以可复用服务组织架构。UML 可表达其中所需的结构与行为，不强迫整个系统只有一种范式。

分析数据不是把所有名词变成类，而是先弄清信息是什么、属于谁、谁维护规则。课件 p128 的金字塔从数据设计向上到架构、接口和组件，提示上层设计依赖数据含义；它不是不可回退的工序。需求改变时必须回到用例和数据模型。

本章要点：先确定模型要回答的问题；分清系统服务与内部实现；用明确责任和契约控制复杂性。

## 2. 对象、类、属性与操作

### 2.1 从具体账户到抽象类

一个账户 `a101` 有当前余额 100 欧元，另一个账户 `a102` 也有 100 欧元。余额相等不代表二者是同一个账户。对象（Object；Objet）具有身份（Identity；Identité）、状态（State；État）和行为（Behavior；Comportement）。身份区分实体，状态是当前属性值，行为是对象允许执行的操作。课件所说对象“不可分”是要求在当前模型中把它作为完整责任单位，不表示对象内部不能含其他对象。

类（Class；Classe）描述一组对象共有的属性、操作、约束和关系；对象是类的实例（Instance）。`Account` 是分类，`a101:Account` 是具体实例。属性（Attribute；Attribut）是描述状态的特征，如余额；操作（Operation；Opération）是可请求的行为契约，如取款；方法（Method；Méthode）是该操作的一种实现。UML 操作不必须一一对应 C++ 源码函数，但设计层常这样映射。

抽象数据类型（Abstract Data Type，ADT；Type abstrait de données）通过可用操作及其含义定义类型，而不暴露表示。账户允许存款和取款，内部用整数分而不是浮点欧元，这是可隐藏的实现细节。接口（Interface）描述可请求的能力；在一般讨论中，“类的公开接口”可以是它的 public 成员集合，在 UML 元素意义上，Interface 是显式定义契约的分类器。

### 2.2 封装与不变量

封装（Encapsulation）使状态修改通过能维护规则的操作发生。不变量（Invariant；Invariant）是每个可观察的稳定状态都应满足的条件，如余额非负。前置条件（Precondition；Précondition）规定合法调用需要什么；后置条件（Postcondition；Postcondition）规定操作正常完成后承诺什么。失败也应有明确结果，而不是隐含地让状态损坏。

```cpp
#include <cstdint>
#include <stdexcept>

class Account {
    std::int64_t balanceCents_;
public:
    explicit Account(std::int64_t initial) : balanceCents_(initial) {
        if (initial < 0) throw std::invalid_argument("negative balance");
    }
    std::int64_t balance() const noexcept { return balanceCents_; }
    bool withdraw(std::int64_t amount) {
        if (amount <= 0 || amount > balanceCents_) return false;
        balanceCents_ -= amount;
        return true;
    }
};
```

这个 C++17 示例以整数“分”计金额。构造函数建立初始不变量；`const` 查询不修改对象；`withdraw` 只在正金额且余额足够时改变状态。账户 10000 分取 3000 分，返回 true 并剩 7000 分；再取 8000 分，返回 false，余额仍为 7000。`explicit` 防止整数无意间转换成账户，`noexcept` 表达查询不抛出异常。并发账户更新还需同步，此小例只讨论单线程。

### 2.3 从自然语言提取模型的步骤

读“教务人员按姓名查询某课程的成绩”：教务人员是外部角色；姓名和课程名是输入；学生目录和成绩存储是内部协作者；PASS 是对外服务。姓名可作为字符串属性，不应因为是名词就建立 `NameManager` 类。若姓名具有复杂规则或独立生命周期，才需要进一步建模。

候选类通常是有身份、持续状态或独立规则的事物；候选属性是描述事物的值；动词提示操作；“拥有、引用、属于、由……组成、是一种”提示关系。然后逐项追问：是否要独立查询或维护？是谁负责更新？同一实体能否被多个对象共享？删除一方是否应删除另一方？数量是每一时刻还是历史累计？这些答案比语法上的名词和动词更重要。

从具体实例归纳类时，也要避免反向错误：法国、西班牙、阿尔及利亚、摩洛哥属于 `Country` 的实例，不是四种子类。泛化用于可替换的不同类型，不能用于枚举四个具体实体。

## 3. 一套模型，多个视图

### 3.1 课程分类与标准分类

课件 cours2 p14–19 的五个“静态视图”是用例、类、对象、组件、部署；四个动态视图是时序、协作、状态转换、活动。它按教学关注点分类，并把功能需求图放在静态部分。标准 UML 将用例图归入**行为图**，交互图又是行为图的子类。包图出现在课件“其他图”部分，也属于标准结构图。不要把这两套分类混为一个标准。

**补充：UML 2.5.1 常用完整图种分类（14 种）。**

| 大类 | 图种 | 主要回答的问题 |
|---|---|---|
| 结构图 Structure / Structure | 类、对象、包、组件、复合结构、部署、轮廓 | 系统由什么构成，怎样连接与组织？ |
| 行为图 Behavior / Comportement | 用例、活动、状态机 | 系统提供什么、工作怎样流动、对象怎样响应事件？ |
| 交互图 Interaction / Interaction（行为子类） | 时序、通信、交互概览、时间 | 协作者怎样交换消息，顺序及时间约束是什么？ |

图 1：交互图包含在行为图中。轮廓、复合结构、交互概览与时间图属于补充，不替代课程核心图。

### 3.2 4+1 架构视图

cours1 p131 与 cours2 p14–19 把用例放在中心，并展示逻辑、进程、实现、部署四个视图。用例说明场景和系统目标；逻辑视图说明类与协作；进程视图说明并发任务、线程和同步；实现视图说明包、库和组件组织；部署视图说明任务放在哪些机器和处理器上、通过何种网络通信。这里“进程视图”不等于“一张时序图”；时序可以帮助研究它，但还需明确并发执行者。

类图不能告诉你取款消息的次序，时序图不能枚举所有合法状态，部署图不能替代业务类图。它们是同一系统的不同投影，因此命名、类型、操作和约束要一致。所谓时序与通信图“同构”是课件对同一交互换一种表达的说法；现代 UML 中复杂片段与时间约束的表达能力不能无条件等同。

## 4. 用例图：从使用者目标确定系统边界

### 4.1 先站在系统外面

用例（Use Case；Cas d'utilisation）描述系统与参与者交互、产生对参与者有价值结果的一组行为。参与者（Actor；Acteur）是系统外部承担某角色的人、设备或其他系统。同一个人可承担“顾客”和“管理员”两种角色；参与者不是人物档案类。外部支付服务也是参与者。

系统边界画成命名矩形，角色画在外部，用例画成内部椭圆。连接角色与用例的实线表示参与，不表示时间先后，也不是 C++ 指针。用例名用目标性的动宾词组，如“查询成绩”，通常不要用“按下按钮”代表完整用户目标。

### 4.2 三种用例组织关系

`«include»`（包含；Inclusion）从基础用例指向被包含用例，是虚线加开放箭头，表示执行基础行为时插入被包含的行为。存款和取款都需要认证时，可以共享“客户认证”；结账可包含扫描商品、计算总额与税、支付。顺序仍需用文字场景或时序图给出，不能从三条 include 箭头推断。

`«extend»`（扩展；Extension）从扩展用例指向被扩展的基础用例。在扩展点和条件满足时增加行为；基础用例应可独立定义。例如注册过程中“获得注册帮助”扩展“注册”，结账中的“帮助”扩展“结账”。它不是继承。课件 p26 把“网络转账”指向“转账”并旁注继承，这是一种容易混淆的教学简化；若网络转账是完整转账的特化，应使用泛化；若只是特定扩展点上的附加行为，才用 extend。

泛化（Generalization；Généralisation）是实线空心三角形，三角指向较一般的角色或用例。“注册客户”是一种“访客”，可参与访客的浏览用例，再增加购买能力。一个角色有账户不表示注册操作必须在每次购买中运行；已经注册可作为购买的前置条件。

### 4.3 绘制与阅读方法

先写一句边界定义，如“只建模 ATM 本机软件”；列出外部交互者；列出有业务价值的目标；给每个目标写触发、输入、成功结果、失败结果；最后才整合 include、extend 和泛化。读图时先读边界，再读角色能获得的服务，最后读复用与条件关系。

课件 p25 的 ATM 图有顾客“查询账户”“取款”，技术员“关机／开机”“补充现金”。两条约束不能丢失：取款受现金箱库存限制；技术员补钞前先关闭机器。后者应写进维护场景或状态图，不能只画两条无序实线就认为说明了顺序。p27 的 Checkout 示例还有 Clerk、Payment Service 和 Administrator；管理员管理用户，支付服务参与支付，客户与收银员参与结账。图上的多重性描述关联参与数量，不描述消息发送次数。

常见错误是把数据库等内部实现画成演员、把所有按钮画成用例、把 include 当“之后做”、把 extend 当继承。用例可以按子系统放进包，但边界必须明确：在银行总体系统中内部的 SIC，到了 ATM 软件边界之外又成为外部系统角色。

本章要点：角色依赖边界；椭圆表达服务目标；用例关系不承担完整流程表达任务。

## 5. 类图：把数据与责任放在正确位置

### 5.1 三个分隔区与抽象层次

类图（Class Diagram；Diagramme de classes）描述分类器的静态结构。一个类矩形通常分为名称、属性、操作三个区。只有名称的框不表示类没有属性；它只是隐藏了细节。没有画可见性也不表示全是 public。课件 p35–37 用汽车从名称、属性与行为，到类型和访问级别逐层展开，正是同一个类在不同抽象层次的表示。

![类的标准表示](assert/class-notation.svg)

图 3：Account 包含私有余额、公开查询、受保护操作和静态成员；IWithdraw 是接口。

属性的一般格式是 `[可见性] 名称 : 类型 [多重性] = 默认值 {性质}`。操作格式是 `[可见性] 名称(方向 参数 : 类型 = 默认值, …) : 返回类型 {性质}`。方括号在这里表示可省略部分，真正属性多重性如 `aliases : String [0..*]` 的方括号则会写在图里。

| 符号 | 意义 | C++17 对应与限制 |
|---|---|---|
| `+` | public / public | `public:` |
| `-` | private / privé | `private:` |
| `#` | protected / protégé | `protected:` |
| `~` | package / paquetage（补充） | C++ 没有直接对应访问级别 |
| 成员下划线 | 静态，属于分类器而非每个实例 | `static`；不是对象名下划线 |
| 类名或操作名斜体、`{abstract}` | 抽象类或抽象操作 | 含纯虚函数的类、`= 0` |
| `/total` | 派生属性，由其他数据计算 | 可用 getter 计算，不要求存储字段 |
| `{readOnly}` | 只读性质 | `const` 或无修改接口，具体实现需分析 |
| `{query}` | 查询操作，不改变模型状态 | 常映射 `const`，但 const 不能自动证明所有外部状态都不变 |
| `{id}` | 标识属性 | 唯一标识；不等于内存地址 |

参数方向 `in` 是输入，`out` 是输出，`inout` 是输入并被修改，`return` 是返回参数。C++ 可分别使用值／const 引用、非 const 引用、返回值表达；不能机械认为“所有引用都代表 inout”。默认值示例 `drive(to : String = "Brest")` 表示省略参数时使用该值。汽车课件还包含注册号、颜色、品牌、功率、重量、日期、所有者，和启动、点火状态查询、驾驶、出售；它说明一张图可同时表达领域信息与操作，但正式设计中所有者更适合关系而非随意写成名字字符串。

### 5.2 抽象、接口、泛型与构造型

抽象类不可直接实例化，可含共享状态与实现。接口（Interface）定义一组公开特征和契约，实现者承诺提供它们；类用虚线空心三角指向接口，称实现（Realization；Réalisation）。接口也可表示成提供接口的圆球、需要接口的半圆插口。

```cpp
struct IWithdraw {
    virtual ~IWithdraw() = default;
    virtual bool withdraw(long long cents) = 0;
};
```

`virtual` 支持通过基类引用／指针调用具体实现；`= 0` 是纯虚操作；虚析构函数使经基类指针销毁派生对象正确。`override` 可验证派生函数确实重写。按值保存基类会发生对象切片，无法保留派生部分；因此多态集合通常保存指针形式。

构造型（Stereotype；Stéréotype）用 `«…»` 表示领域扩展，如课件 `«thread»`、`«utility»`、`«event»`、`«meta-class»` 与图书 `«entity»`。**补充：**构造型应来自明确轮廓及约定，不能凭双尖括号把任意词自动变成 UML 标准元素；`«interface»` 等也常用于关键字式表示。附加性质和约束写在花括号，注释用折角便笺连接目标。它们分别是类别、性质与说明，不要混用。

泛型（Genericity；Généricité）或参数化类用模板签名表示未绑定的类型参数。课件的 `Liste<Element>` 绑定为 `Liste<ObjetGraphique>`，绑定依赖指向模板，标 `«bind» <Element -> ObjetGraphique>`。C++ `template<class T> class List` 对应模板定义，`List<GraphicObject>` 对应类型实参绑定。模板实例化不是在运行时创建某个对象。

<a id="relationships"></a>
## 6. 类之间的关系：线条必须有可验证含义

### 6.1 关联与依赖

关联（Association）描述对象之间可以存在的语义连接；具体对象之间的连接叫链接（Link；Lien）。`Person -- Company` 表示工作关系，某个张三对象与某公司对象之间的雇佣链接是其一个实例。关联通常画实线，可标关联名称、两端角色、多重性和导航性。

依赖（Dependency；Dépendance）表示一个元素的定义或行为依赖另一个元素，后者改变可能迫使前者改变。虚线开放箭头从使用者（client）指向供应者（supplier）。窗口处理 `MouseEvent` 参数，而不长期保存事件对象，常画 `Window ..> MouseEvent`。不要因为 A 的函数会调用 B 就断定必须是组合，也不要把实线导航箭头当成虚线依赖。

### 6.2 多重性怎样读才不会颠倒

多重性（Multiplicity；Multiplicité，课件也称 Cardinalité）约束一个固定的对端对象可连接多少本端对象。`Company "0..3" -- "0..*" Person` 中，公司端的 `0..3` 表示每个人最多三个雇主；人端 `0..*` 表示每家公司可雇用零到多人。它约束有效状态，不是历史总人数，也不是图上必须画多少矩形。

`1` 恰好一个；`0..1` 可选单个；`*` 等于 `0..*`；`1..*` 至少一个；`2..*` 至少两个；`3` 恰好三个。课件的 `1..n` 应在正式图中把 n 定义为参数或改成 `1..*`，不能把未定义的 n 当标准无限符号。

课件 p40 的男女婚姻例子两端 `0..1` 是特定简化业务规则，不是 UML 对婚姻的普遍规定；Person–House 的房屋端 `1` 是每人一处房屋的假设，不能从现实自动推出。Person 自关联中 parent 端 `2`、child 端 `0..*` 表示每人恰有两名已登记父母并可有多个孩子，这依赖完整登记假设；未知父母应允许 `0..2` 或显式未知记录。

### 6.3 导航性、角色与读名方向

导航性（Navigability；Navigabilité）说明能否从一个对象访问关联另一端。`Voter --> Candidate` 表示投票者可以访问所投候选人，候选人不因此必然保存投票者集合。单向箭头并不说明所有权。无箭头可按图的约定省略导航信息；不要无条件读成双向。**补充：**显式不可导航可在端点画叉号，画图前需声明工具约定。

角色（Role；Rôle）是对象在关系中的位置名，如雇佣关系中的 `employee` 与 `employer`，酒店中的 `guest` 与 `staff`。名称旁的小实心三角仅指示关联名的阅读方向：`Hotel héberge Person` 表示“酒店接待人”，不代表 Hotel 可导航到 Person。需要导航则在线端另画开放箭头。

### 6.4 聚合与组合

共享聚合（Shared Aggregation；Agrégation）是整体—部分关系，空心菱形放在整体端。课件房间 Pièce–墙 Mur 的例子允许多个房间共享墙；销毁“房间模型”不必销毁墙。标准对共享聚合没有统一强生命周期语义，因此必须说明业务含义；当它不增加信息时，普通关联更清楚。课件称“强耦合”是教学描述，不能据此把它与组合的所有权等同。

组合（Composite Aggregation / Composition）用实心菱形放在整体端，表达部件同时至多属于一个组合整体，并由整体承担部件的存在／销毁责任。销毁整体会销毁当时仍包含的部件；部件可以先脱离整体或转移，前提是约束允许。课件汽车—车身—发动机—活塞表现嵌套组合；汽车包含车身及发动机，发动机包含活塞。必须按软件模型判断：可维修并独立库存的发动机可能应是普通关联，不应仅因为现实“安装在车里”就强制组合。

**标准语义修正：**组合不要求“物理包含”，也不规定复制整体时必须深复制部件。C++ 类是否可复制、如何克隆，由实现契约决定。使用 `unique_ptr` 的类通常不能直接复制；这仍完全可以实现组合。

![常见类关系](assert/class-relations.svg)

图 4：菱形始终在整体端；三角始终在一般类或接口端；普通开放箭头只表示该线型下的导航或依赖含义。

### 6.5 泛化与实现

泛化／继承（Generalization / Inheritance；Généralisation / Héritage）表示特殊分类器是一般分类器的一种。实线空心三角指向一般分类器。专业化（Specialization；Spécialisation）是从一般类向特殊类细分的分析过程，泛化是从相似类抽取共同概念；图上关系相同。

课件 p49：作品分为书、电影、歌剧，书继续分小说与漫画；车辆可泛化汽车、船与飞机。子类应继承适用契约，新增特征。如“汽车有发动机”是包含关系，发动机不是汽车子类。实现则是虚线空心三角，具体类承诺满足接口；同一个类可实现多个接口。

| 关系 | 想表达的句子 | 线型与端点 | 不足以成立的理由 |
|---|---|---|---|
| 关联 | A 的对象与 B 的对象有业务连接 | 实线，可有导航箭头 | 两类刚好出现在同一文件 |
| 依赖 | A 使用 B 的定义或服务 | 虚线开放箭头 A→B | A 与 B 拥有相同生命周期 |
| 共享聚合 | A 是整体，B 是可共享部件 | 实线空心菱形在 A | A 有一个 B 指针 |
| 组合 | A 负责其独占部件 B | 实线实心菱形在 A | B 安装在实体 A 中 |
| 泛化 | B 可作为 A 的一种 | 实线空心三角 B→A | 只想复用几段代码 |
| 实现 | B 提供接口 A 的契约 | 虚线空心三角 B→A | B 暂时调用 A 的一个方法 |

### 6.6 自关联、三元关联与关联类

自关联连接同一个类的不同实例，如邻国、父母子女、嵌套群组。一定标角色，否则读者无法区分“上级”和“下级”。

n 元关联（n-ary Association；Association n-aire）用中心菱形连接三个以上参与端。cours2 p42 的 Travaux（工程）、Copropriété（共有物业）与 Entreprise（企业）描述三者共同的一项关系。中心菱形没有放在某个类端，绝不能误读为聚合。把它拆成三个二元关系可能产生虚假的组合：企业 A 为物业 X 执行工程 T，与企业 B 为物业 Y 执行工程 T，不代表 A 也服务 Y。多元关联的某端多重性是在其他端实例组合固定时读，因此更需说明上下文。

**补充：**关联类（Association Class；Classe d'association）是本身有属性的关联，如“学生选课”带选课时间和成绩。标准图用虚线把类框连到关联线；若同一学生可多次选同一课程，独立 `Enrollment` 实体加两条关联通常更合适，因为必须区分每次记录。这也是借阅、维修、购买记录不应随意简化为一个布尔属性的原因。

### 6.7 约束补足线条无法表达的规则

`{ordered}`（有序；Ordonnée）说明关联端集合有顺序，课件画家的一组画可按展示顺序排列；不自动等于“按名称排序”。`{subsets soldiers}`（子集；Sous-ensemble）说明将军集合包含在军人集合中。`{xor}`（互斥；Ou exclusif）说明同一上下文中两条关系不能同时成立，例如课程 BTS 模型中某人不能同时以教师和学生身份参与；若真实需求允许兼任，则不应保留该约束。异或究竟要求恰好一条还是最多一条，需结合端的下限与文字说明。

大括号可写自然语言约束，也可写正式约束语言 OCL（Object Constraint Language；补充）。不需要先学 OCL 才能精确建模：写“维修需要的技能集合必须包含在执行机械师的技能集合中”已经比漏掉规则准确。`{unique}` 与 `{nonunique}` 控制集合能否重复，`{readOnly}` 控制是否可修改，均不能用箭头代替。

本章要点：先判断身份、数量、可访问性与生命周期，再选线条；多重性读对端；实现形式不能反过来决定业务语义。

## 7. 从类图映射到 C++17

### 7.1 值、引用与所有权

变量保存值，指针保存对象地址，引用提供另一个对象的别名。对象生命周期是构造完成到销毁之间的时间。拥有者负责销毁；观察者只访问，不能任意销毁。指针非空不保证对象仍活着，因此非拥有关系必须约定目标活得更久或通过可检查机制访问。

```cpp
#include <memory>
#include <string>
#include <utility>
#include <vector>

struct Wall { int id; };
struct Engine { int powerKW; };
struct Driver { std::string name; };

class Car {
    std::unique_ptr<Engine> engine_; // 独占拥有：组合的一种实现
    Driver* driver_ = nullptr;      // 非拥有可选关联：0..1
public:
    explicit Car(int kw) : engine_(std::make_unique<Engine>(Engine{kw})) {}
    void assignDriver(Driver& d) noexcept { driver_ = &d; }
    int power() const noexcept { return engine_->powerKW; }
};

class Room {
    std::vector<std::shared_ptr<Wall>> walls_; // 允许房间共享墙
public:
    explicit Room(std::vector<std::shared_ptr<Wall>> w) : walls_(std::move(w)) {}
};
```

`unique_ptr` 离开作用域时销毁所拥有对象，拷贝被禁止，移动转移所有权。`shared_ptr` 通过引用计数协调多个拥有者，最后一个拥有者消失才销毁目标；循环拥有可能导致资源无法释放，可用 `weak_ptr` 表示可检查的观察关系。它们不是 UML 符号的机械编码：普通关联也可用 shared_ptr，聚合也可用外部统一拥有的裸指针；关键是契约。

一个必需、稳定的非拥有关系可用 `T&` 实现 `1`；可空指针可实现 `0..1`；`vector<T>` 或 `vector<unique_ptr<T>>` 可实现拥有的多值关系；`vector<T*>` 可以观察多个外部对象。容器不会自动保证 `2..*` 或最大三项，构造、增删操作必须检查规则。

### 7.2 双向关系需要维护一致性

若 Person 保存雇主列表，Company 也保存员工列表，雇佣和解雇必须同时更新两侧。只更新一边会使对象图不符合类图约束。实际实现可让一处 `EmploymentService` 或 `Employment` 记录统一维护两端；不需要为了“一切面向对象”就把所有链接复制到两边。

依赖常体现为参数类型、局部变量或函数调用；泛化常体现为 `class Derived : public Base`；实现常体现为继承纯虚接口。C++ private 继承偏向实现复用，不能直接当公开可替换的领域泛化。模板、重载、异常和内存布局都是代码层选择，若模型没规定，不应宣称它们可从图中唯一推导。

### 7.3 类图不等于数据库表

类有行为契约，对象有身份和生命周期；表主要表达持久化记录。外键可实现关联，连接表可实现多对多，仍必须保持业务约束。模型中的 `StudentDirectory` 与 `MarksDataStorage` 可以是类、远程服务或组件，设计层需要明确当前表达层次，不要把 `String`、每个 getter 和数据库服务器都混在同一张领域图里。

## 8. 对象图：用具体快照检查类图

对象图（Object Diagram；Diagramme d'objets）展示某一时刻的实例、属性值与链接。实例头写成并下划线 `france:Country`，匿名实例可写 `:Country`，没有类型的命名实例可只写名称；值槽（Slot）如 `name = "France"`。下划线强调这是实例，不是类。对象间实线是现存链接，不是未来可能的类型关系。

![邻国对象图](assert/pc-2a-objects.svg)

画图时先选一个有意义的时刻，列出实际实例及其值，按类图允许的关系连接，再核对每个端数量。例如“每组至少两项”的类图若实例组只连接一个对象，该快照就违法。若只画局部内容，要明确省略范围，不能把“省略”与“约束违反”混为一谈。

## 9. 时序图：把一次合作按消息顺序展开

### 9.1 生命线和消息

时序图（Sequence Diagram；Diagramme de séquence）描述一次交互。参与者头下方的虚线叫生命线（Lifeline；Ligne de vie），表示该参与者在交互中的存在；细长矩形是执行规格（Execution Specification，课件称 Bande d'activation），表示正在执行行为或等待嵌套调用完成。竖轴从上到下表达发生顺序，水平位置通常只是排版，不代表重要性。没有时间标尺时，箭头间距离不能当作实际秒数。

同步调用（Synchronous Call；Message synchrone）用实线实心箭头，调用者等待被调行为完成。返回（Reply；Message de retour）用虚线开放箭头，方向由被调者回到调用者，可标结果，省略返回不意味着不返回。异步消息（Asynchronous Message；Message asynchrone）用实线开放箭头，发送后不等待接收者完成；接收是否可丢弃、重试和排队必须在协议中另定义，不是 UML 自动许可“随便忽略”。

![时序符号示例](assert/sequence-notation.svg)

图 6：展示同步、返回、异步、自调用、创建、销毁与条件片段；箭头线型在时序图中不沿用类图含义。

自消息（Self Message）从对象回到自己，可表示内部方法调用，形成嵌套执行。回调（Callback）由之前接受请求的协作者反向通知或调用原请求者；它与自消息不同，且可能同步或异步。创建消息指向新生命线的头，新对象不应在创建前参与交互；销毁在生命线末尾画叉号，之后不能再向该对象发正常消息。创建是对象创建，不是创建一个类。

### 9.2 条件、循环、并行与引用

组合片段（Combined Fragment；Fragment combiné）用框和左上角操作符包围交互区。守卫（Guard；Garde）用 `[条件]` 表示该路径适用条件。

| 操作符 | 含义 | 示例与注意事项 |
|---|---|---|
| `alt` | 互斥可选路径 | `[余额足够]`／`[else]`；不要让成功和失败同时成立 |
| `opt` | 有条件执行一段，否则跳过 | `[要求收据]` 打印收据 |
| `loop` | 按次数或条件重复 | `[每个购物条目]`，说明上下限和终止条件 |
| `par` | 分支事件允许交错并发 | 搜索 Google、Bing、Ask；不表示固定先后 |
| `break` | 条件成立后用此片段替代剩余交互（补充） | 认证失败后的结束 |
| `critical` | 相关生命线上不能与其他事件任意交错（补充） | 原子余额更新；实际还需实现同步 |
| `ref` | 引用已有交互（Interaction Use） | Balance Lookup、Debit Account；不是复制一段文字即可获得实现 |

消息端点的发生规格（Occurrence Specification）区分发送与接收事件；一个异步发送与接收之间可以存在间隔。**补充：**一般只保证每条生命线上所示事件及消息因果约束，不应把独立生命线的每一行都当成全局绝对时刻。时间／时长约束例如 `{10..200 ms}` 约束两个发生点之间的时间。门（Gate）是交互边界上的消息连接点，用于内外交互接续，不是业务参与者。

### 9.3 读图与检查方法

先读场景前置条件与参与者类型，再从上向下追踪每次调用及返回，进入片段时检查守卫，遇到循环时说明遍历集合，最后检查成功与失败后状态。画图应从用例的一条具体场景出发，决定谁负责每步、接收者有哪些操作，再添加返回、循环和异常路径。消息名应与类图操作相容；参数从哪里取得必须可追踪。

例如 PASS 的核心顺序一定是“教务→PASS 查询姓名和课程；PASS→目录查 ID；目录→PASS 返回 ID；PASS→成绩库用 ID 和课程查分；成绩库→PASS 返回列表；PASS→教务返回列表”。若把姓名直接发送给成绩库，就违反题目“不存姓名”的约束。

常见错误包括用继承箭头发送消息，把类别 `Student` 当所有学生共用的单个对象，先出钞后无条件扣款，以及遗漏失败分支仍画成功输出。银行卡、现金和收据是实体或物理输出，画成消息时应说明这是系统与设备／人的交互抽象，而不是它们真是函数返回对象。

## 10. 通信、状态与活动：其他动态观察角度

### 10.1 通信图

通信图（Communication Diagram；Diagramme de communication）是课件“协作图”（Collaboration Diagram；Diagramme de collaboration）的现代名称。它强调参与对象的空间连接，在链接附近标消息方向与序号，例如 `1: request()`、`1.1: findIds()`、`1.2: getMarks()`。小数表示嵌套调用，而不是时间 1.1 秒；循环可标 `*[每项]`。

![PASS 通信图](assert/communication-pass.svg)

图 7：序号承载顺序，布局承载协作结构。此图的对象头带下划线，箭头标签是消息，而不是类操作区。

课件 p72 的飞机 `pa87:Boeing` 状态为遇险，向塔台反复发送 mayday；塔台协调跑道飞机移动到停机区与消防队赴跑道，再允许遇险飞机降落。原图 `1/2.a`、`1/2.b`、`2.a/3` 是旧示例的局部顺序标记，阅读要结合箭头与并发意图，不应当作现代通用数字语法。塔台→飞机的多对象重复消息说明要清空跑道，塔台→消防说明应急支援。此类系统需显式写“跑道清空且可用才着陆”的守卫，空间布局不能证明安全前提已满足。

绘制先画实例与可通信链接，再把时序场景的消息编号移过去；阅读按编号追踪，不能按图左到右读。它适合检查协作者太多、连接太密等结构问题；复杂条件、时间和并行关系通常在时序图更清楚。

### 10.2 状态机图

状态机图（State Machine Diagram；Diagramme états-transitions）观察**一个对象**怎样因事件改变状态。状态是持续的一种配置／情形，如 ATM“待机”“认证中”“可取款”“维护中”，不是一条函数语句。转换格式 `触发 [守卫] / 效果`：收到什么事件，在什么条件下，执行什么动作，然后进入哪个状态。

实心圆是初始伪状态，靶心圆是区域终态；圆角矩形是状态；`entry / …` 在进入时执行，`do / …` 是持续活动，`exit / …` 在离开时执行。复合状态包含子状态。历史伪状态 `H`（浅历史）记录最近子状态，`H*`（深历史）记录更深层配置，属于补充。无触发的完成转换在源行为完成时有资格发生，不能当任意自动跳转。

![课程洗车状态机](assert/state-wash.svg)

图 8：完整洗车复合状态包含洗涤与抛光；两分钟后由洗涤到抛光，四分钟后退出到干燥，再两分钟到终态。复合状态内任何阶段紧急停止都到等待，等待中恢复可返回洗涤入口，等待超时结束；干燥阶段紧急停止直接结束。原图的恢复未画历史伪状态，因此不能读成自动恢复之前的抛光进度。

先识别对象、稳定状态、外部事件和时间事件，再写守卫与效果，最后处理错误、超时和复合状态。读图时固定当前状态，只考虑从它及包含它的状态可离开的转换。常见错误是把多个对象的工作流程当一个对象状态机，把“调用查询函数”当持续状态，或省略恢复到底重新开始还是继续历史。

### 10.3 活动图

活动图（Activity Diagram；Diagramme d'activités）描述工作或计算中的控制流与对象流，适合用例内部步骤、分支、循环和并发协作。课件分类中有活动图但未专页展开；以下符号与实例是**补充**。

![成绩查询活动图](assert/activity-pass.svg)

图 9：按姓名查 ID，若唯一匹配则查成绩并返回；否则返回明确错误。分支条件互斥，最后才结束整个活动。

圆角动作框表示一次动作；箭头传递控制或对象 token（令牌）；菱形决策一个输入按守卫选择输出，合并多个互斥输入为一个输出；粗条 fork 将控制并发分流，join 等待必要分支同步。决策／合并与 fork／join 不能互换。实心圆启动活动，靶心 Activity Final 结束整个活动，圈内叉 Flow Final 只结束一条流。泳道（Partition；Couloir）划分责任，不是线程声明。对象节点矩形可显示传递的数据，如 StudentId 或 Marks。

画图先写动作，再标执行责任、条件、循环与并行同步，最后区分何时整个活动结束。不要为了画并行而把必须“先查 ID、再查成绩”的步骤 fork；后一动作依赖前者结果。状态图重在对象情形与事件，活动图重在步骤和流，两者可用于同一业务但回答不同问题。

## 11. 包、组件、部署与补充图种

### 11.1 包图

包图（Package Diagram；Diagramme de paquetages）用带小标签的文件夹框把模型元素放入命名空间。它组织逻辑模块，不代表一个运行对象，也不天然是一个动态库。嵌套表达层级；依赖箭头说明一包元素使用另一包。

![包图与组件图](assert/packages-components.svg)

图 10：接口层依赖应用服务，应用服务依赖领域和存储接口；存储实现提供接口。逻辑分层和运行组件是两个表达层面。

**补充：**`«import»` 导入公开可见成员，`«access»` 作私有导入；`«merge»` 合并包定义，不能当“复制文件”。课件 p69 的 P3→P1 空心三角被称“继承”，现代标准包图更适合按实际目的使用包合并、导入或依赖，不能直接把 C++ 类继承套到命名空间。C++ namespace 可对应逻辑包，但并不一一等同。

画图先按责任分组，再画跨包依赖，检查循环依赖与暴露范围。读图从层次看包含，再按箭头看谁受谁的改变影响。文件夹相邻不表示通信，包的嵌套也不表示生命周期组合。

### 11.2 组件图

组件图（Component Diagram；Diagramme de composants）表示封装且可替换的实现单元、提供与需要的接口及连接。组件可用矩形加右上角组件小图标或 `«component»`。提供接口是球形，所需接口是插口；组装连接把相容服务接起来。端口（Port）是边界上的小方框，组织交互点；委派连接把外部端口的请求送到内部部件。

一个 `PASS Service` 提供查询接口并需要目录和成绩接口；更换成绩库实现而保持接口契约，调用方可以不变。C++ 静态库、DLL 或服务可成为实现组件，组件不是任何 `.cpp` 的同义词。课件 p70 旧图用组件形状画头文件、源文件、`.obj` 与任务，是编译组织实例；现代 UML 中具体文件更宜标为制品（Artifact；Artefact），制品实现／体现组件。

![PASS 组件与提供接口](assert/components-pass.svg)

图 10b：矩形右上角的小组件图标标识实现单元，圆球标识提供接口。PASS 对 StudentLookup 与 MarksQuery 的虚线 `«use»` 箭头表达所需服务，箭头指向被使用接口；这与把所需接口画成插口是两种表达方式，不能把虚线误读为提供接口。图中没有画组装连接，故不据此推断部署位置或通信协议。

绘制先识别可替换单元和服务契约，再列出提供／需要接口，再接线；阅读先服务后依赖。不能把菱形表示的类组合误当组件插口，也不能因为两组件有线就假定同进程。

### 11.3 部署图

部署图（Deployment Diagram；Diagramme de déploiement）把制品放到节点上，回答“运行在哪里，节点怎样通信”。三维盒表示节点（Node；Nœud），`«device»` 设备节点如 ATM，`«executionEnvironment»` 执行环境如操作系统或进程容器；折角文件矩形表示制品，`«deploy»` 可表达部署依赖；节点间实线通信路径可标 TCP/IP、CAN 等协议。

![ATM 部署示例](assert/deployment-atm.svg)

图 11：本机软件部署在 ATM，路由服务部署在路由节点，银行服务部署在银行节点。线上的网络协议不是类之间的继承。

课件 p71 的工业系统有实时系统与 CTask 多实例、CAN 接口盒、三台机器人、传感器／执行器、交换机、监督 PC、数据库 PC、SQL 服务、数据库及 ADSL 路由器连互联网。CAN 与 TCP/IP 线区分现场控制与管理网络，节点内符号表示驻留任务或服务。逻辑线程和物理设备要分别标清；一个机器可跑多个任务，一个任务也可能随部署方案转移机器。

第一份课件与 UML 相关的架构基础只保留到能理解这些图的程度：分层通过下层接口提供服务、封装实现并促进复用；客户端／服务端让多个客户端请求中心服务，集中维护但有服务器负载问题；多层部署可分表示、业务、数据访问，由通信中间层连接，考虑平台差异、数据保护和负载分配。逻辑 layer 与物理 tier 不一一对应。数据、呈现和协调职责分离有助于分别修改界面与业务，但本书不展开 MVC 设计模式。

### 11.4 复合结构图（补充）

复合结构图（Composite Structure Diagram；Diagramme de structure composite）展开一个结构化分类器内部的部件、端口与连接器。类图告诉你 ATM 类型有设备关系，这张图告诉你“这个 ATM 内部哪个端口连接哪个部件”。部件写 `reader:CardReader [1]`，端口用边界小方框，连接器表示角色间的通信路径；组装与委派连接的含义同组件结构。

![ATM 内部结构](assert/composite-structure.svg)

图 12：ATM 外部端口委派到控制部件，控制部件连接读卡器和出钞器。部件是分类器内部的角色，不能把所有矩形都当独立服务器。先定边界与对外端口，再划内部职责、数量和连接；阅读由外部端口沿委派进入内部。仅需表达类型关系时用类图更直接。

### 11.5 轮廓图（补充）

轮廓图（Profile Diagram；Diagramme de profils）定义如何按领域扩展 UML。轮廓包含构造型、标记性质及约束；构造型通过扩展（Extension）连接被扩展的元类（Metaclass）。这条扩展线的实心箭头与类图继承的空心三角不同。

![轮廓图示例](assert/profile.svg)

### 11.6 交互概览图与时间图（补充）

交互概览图（Interaction Overview Diagram；Diagramme global d'interaction）用活动式控制结构组织多个完整交互。框中的 `ref Authenticate`、`ref Withdraw` 分别引用时序交互，菱形控制它们的条件顺序。它适合多场景导航，不替代每个交互内部的详细消息。

![交互概览](assert/interaction-overview.svg)

时间图（Timing Diagram；Diagramme de temps）强调状态／值在明确时间轴上的变化。生命线可以画成不同状态高度的阶梯曲线，横轴才是时间；状态段、变化点和持续时长约束共同说明何时必须响应。

<a id="design-principles"></a>
## 12. 怎样判断类图设计合理：耦合、内聚与 SOLID

### 12.1 看变化会传播到哪里

耦合（Coupling；Couplage）是单元彼此依赖的程度与性质；内聚（Cohesion；Cohésion）是一个单元内部特征围绕共同职责的紧密程度。把查询流程放在 PASS，把姓名索引放在目录，把成绩放在存储，是职责内聚；让开关只依赖开关能力，避免牵连能耗算法，是限制耦合。依赖数量少不自动好：一个巨大类零外部依赖，也可能极难维护。

课件 cours1 p126 的“内部高频联系，外部低频联系”提示把紧密协作的东西放在同一边界，以稳定服务连接边界；这里频率是启发式，不是必须最小化函数调用次数的公式。类职责应有清晰变化理由，接口不应暴露不相关操作。模块化有助于复用、可扩展、可理解、信息隐藏与协作，但错误和异常不会因为拆类自动隔离，必须定义失败契约。

### 12.2 五条原则的可操作含义

单一职责原则（Single Responsibility Principle，SRP；Principe de responsabilité unique）要求一个模块围绕一种责任／变化原因。不是每类只能有一个方法。Person 的身份变化和邮箱语法规则变化来自不同原因，邮箱值类型可承担验证。

开闭原则（Open–Closed Principle，OCP；Principe ouvert/fermé）要求对预期扩展开放、对稳定核心修改关闭。年龄规则从单一阈值变成按国家配置时，可以让稳定检查器使用阈值数据；没必要每新增国家就修改一段 switch。它不意味着任何代码永远不能改，而是选择值得稳定的边界。

里氏替换原则（Liskov Substitution Principle，LSP；Principe de substitution de Liskov）要求用子类型替代父类型时，依赖父类型契约的正确客户端仍正确。子类型不能加强前置条件、削弱后置条件或破坏不变量。几何上正方形属于矩形，并不证明可变 `Square` 能替代提供独立宽高设置的 `Rectangle`。

接口隔离原则（Interface Segregation Principle，ISP；Principe de ségrégation des interfaces）要求客户端不被迫依赖不使用的能力。数学教师依赖 `MathLearner`，不是带钢琴和小说方法的整个 Student 类型；学生本身仍可以实现多种能力。

依赖倒置原则（Dependency Inversion Principle，DIP；Principe d'inversion des dépendances）让高层业务与低层细节依赖合适的抽象，抽象不依赖具体实现细节。Application 使用 `ILogger`，具体 FileLogger 实现它。依赖注入（Dependency Injection；补充）是从外部传入协作者的一种实现方式，不等于 DIP 本身。若传入的仍是具体 FileLogger，注入发生了但倒置未必发生。

### 12.3 从图到契约的检查链

从一条用例开始，确认类图上有实现目标所需的信息与能力；用时序图检查每条消息接收方确实有操作；用对象图检查数量和链接；用状态图检查操作在此状态允许；最后分析某项需求变化会迫使哪些类修改。所谓合理设计是“满足明确需求，并在预计变化下保持契约清晰”，不是箭头越多、接口越多就越高级。

<a id="workflow"></a>
## 13. 把需求一步步变成一致模型

课程 cours1 p132–148 的流程可整理成可反复回退的十一项工作：

1. 识别边界外演员，区分人员、设备、外部系统。
2. 写场景、目标、输入输出和交互，含失败情况。
3. 按功能群识别信息类型，检查不同功能是否使用同一业务实体。
4. 把允许的操作放到能维护信息规则的责任对象。
5. 识别关系及数量、生命周期与通信参数类型。
6. 用时序或通信图展开场景，检查同步、消息与职责。
7. 明确类的公开接口，而非先把所有字段 public。
8. 识别协作所需的关系与数据引用。
9. 加入类内部专有状态与操作。
10. 指定构造、销毁、所有权及复制策略。
11. 指定必要的内部同步和失败契约，再实现每个方法中的算法。

例如 PASS 的姓名查找可能发现重名，此时回到第 2 项补充“零匹配／多匹配”结果，而不是默默在实现里选第一个学生。原需求没有定义重名处理，这就是模型暴露的问题。自顶向下从目标走向场景，自底向上从具体场景归纳共享能力，两条路线应汇合。

详细设计记录应有目标、输入、输出、处理与验证场景。先确定要得到什么输出，再判断需要什么输入，最后决定处理，是课件 p64 “输出→输入→处理”的规划思路，不是程序执行顺序。新需求出现后返回用例，逐步演进模型。课程提及 RUP（Rational Unified Process）与模型驱动开发（Model Driven Software Development），这里只保留“过程可使用 UML、模型可指导实现”的联系；UML 本身不是 RUP，也不规定必须自动生成代码。

下面把全部课程习题作为完整建模案例展开。题目没有明确的数量、生命周期或失败规则会标明“建模假设”；额外完善不会冒充原题条件。

## 14. cours2 课件案例与完整解答

### 14.1 购物网站：用例图（p28–29）

### 14.4 Bag 折扣：跨图一致性（p66）

**完整题意。**Bag 引用一组 Item，对 Bag 应用 −20% 促销意味着给每个被引用 Item 都设置 −20% 促销。要求类图与时序图。

![Bag 类图答案](assert/bag-classes.svg)

![Bag 时序答案](assert/bag-sequence.svg)

图 19：Bag 的 `applyPromotion` 遍历 items，每次向对应 Item 发送 `setPromotion(-0.20)`。

题目只说“引用”，没有说拥有，使用导航关联即可。Bag 端的多个表示本方案允许一个 Item 被多 Bag 引用，这是明确的可共享假设；若禁止共享可改为 `0..1`。时序中的 item 是循环当前接收者，不是永远向同一个 item 重复设置。必须保证类图操作与消息名一致。若共享 Item，促销会影响所有引用它的 Bag；若只想折扣某个购物车条目，应把折扣放在条目，而不是全局商品。

```cpp
#include <stdexcept>
#include <vector>
class Item {
    double promotion_ = 0.0;
public:
    void setPromotion(double rate) {
        if (rate < -1.0 || rate > 0.0) throw std::invalid_argument("invalid rate");
        promotion_ = rate;
    }
    double promotion() const noexcept { return promotion_; }
};
class Bag {
    std::vector<Item*> items_;
public:
    void add(Item& item) { items_.push_back(&item); }
    void applyPromotion(double rate) {
        for (auto* item : items_) item->setPromotion(rate);
    }
};
```

Bag 不拥有 Item，调用者保证 Item 活得更久。`add` 只接收引用，所以此接口不会加入空指针。该代码是促销设置示例，不计算货币。−0.20 代表相对原价减少 20%，不是连续两次调用变成减少 40%；setter 覆盖同一促销值。

```cpp
#include <memory>
#include <stdexcept>
#include <utility>
#include <vector>
struct GraphicObject {
    virtual ~GraphicObject() = default;
    virtual void draw() const = 0;
};
class Group final : public GraphicObject {
    std::vector<std::unique_ptr<GraphicObject>> children_;
public:
    explicit Group(std::vector<std::unique_ptr<GraphicObject>> children)
        : children_(std::move(children)) {
        if (children_.size() < 2) throw std::invalid_argument("group needs 2 children");
        for (const auto& p : children_)
            if (!p) throw std::invalid_argument("null child");
    }
    void draw() const override {
        for (const auto& p : children_) p->draw();
    }
};
```

容器独占孩子，构造检查两项与非空，draw 通过虚调用执行每项行为。代码没有暴露可随意 add/remove 的接口，也没有暴露反向拥有指针，所以调用者不能通过本接口制造自包含环。若增加移动／重组 API，仍需保持树结构和下限；智能指针本身不是全部业务规则的证明。

![4.2 类图答案](assert/pc-42-classes.svg)

![4.2 时序答案](assert/pc-42-sequence.svg)

图 45：姓名只进入目录查询，成绩存储仅接受整数 ID 和课程字符串。

StudentRecord 保存 name、id。MarksDataStorage 的 MarkRecord 只含 studentId、course、value，因此不会出现姓名冗余；每个条目代表一次成绩，同课可有多成绩，不能只写 `map<id,double>` 丢掉课程维度或多次记录。PASS 引用目录和存储，每个服务可被多客户端调用，不代表只能保存一个学生。

消息完整次序是 Staff→PASS query；PASS→Directory findIds；Directory 返回候选 ID；恰好一个时 PASS→Storage getMarks，Storage 返回列表，PASS 把列表返回 Staff。零匹配和多匹配返回不同错误。这两条错误是补充，因为原题没有给重名规则。不能把姓名称作天然唯一 ID。成绩空列表表示学生存在但课程暂无成绩，不应与学生不存在混淆；课程是否允许空字符串可在接口中加前置条件。

```cpp
#include <map>
#include <stdexcept>
#include <string>
#include <utility>
#include <vector>

class StudentDirectory {
    std::multimap<std::string, int> records_;
public:
    void add(std::string name, int id) { records_.emplace(std::move(name), id); }
    std::vector<int> findIds(const std::string& name) const {
        std::vector<int> result;
        const auto range = records_.equal_range(name);
        for (auto it = range.first; it != range.second; ++it) result.push_back(it->second);
        return result;
    }
};
class MarksDataStorage {
    std::map<std::pair<int, std::string>, std::vector<double>> records_;
public:
    void add(int id, std::string course, double mark) {
        records_[{id, std::move(course)}].push_back(mark);
    }
    std::vector<double> getMarks(int id, const std::string& course) const {
        auto it = records_.find({id, course});
        return it == records_.end() ? std::vector<double>{} : it->second;
    }
};
class PASS {
    const StudentDirectory& directory_;
    const MarksDataStorage& storage_;
public:
    PASS(const StudentDirectory& d, const MarksDataStorage& s) : directory_(d), storage_(s) {}
    std::vector<double> query(const std::string& name, const std::string& course) const {
        const auto ids = directory_.findIds(name);
        if (ids.empty()) throw std::runtime_error("student not found");
        if (ids.size() != 1) throw std::runtime_error("ambiguous name");
        return storage_.getMarks(ids.front(), course);
    }
};
```

`multimap` 允许同名多学生，`equal_range` 给出该姓名范围；`pair<int,string>` 用 ID 与课程组成查询键，值是成绩列表。两个 const 引用实现非拥有必需关系，它们必须比 PASS 活得久。返回值是列表副本，调用者不能借查询接口篡改存储。目录 ID 全局唯一、成绩 ID 必须已登记，在此简化例中由录入边界维护，代码不冒充完整注册管理系统。

![5b 改进答案](assert/pc-5b-after.svg)

图 47：检查流程稳定，国家最低年龄存在 AgeRules 配置中，输入必须提供国家上下文。

单参数 age 不包含国家，无法唯一决定结果。不断在方法里新增 `if country == ...` 会使每次扩展修改稳定代码。若所有规则就是最低年龄比较，配置表加国家足够；检查器只取对应阈值并比较。未知国家应返回明确错误或拒绝处理，不能悄悄用法国阈值。阈值数据的批准与更新是外部业务责任。

```cpp
#include <map>
#include <stdexcept>
#include <string>
#include <utility>
class AgeRules {
    std::map<std::string, int> minimum_;
public:
    explicit AgeRules(std::map<std::string, int> values) : minimum_(std::move(values)) {
        for (const auto& pair : minimum_)
            if (pair.second < 0) throw std::invalid_argument("negative threshold");
    }
    int minimumFor(const std::string& country) const { return minimum_.at(country); }
};
class AgeChecking {
    const AgeRules& rules_;
public:
    explicit AgeChecking(const AgeRules& rules) : rules_(rules) {}
    bool isOldEnough(int age, const std::string& country) const {
        if (age < 0) throw std::invalid_argument("negative age");
        return age >= rules_.minimumFor(country);
    }
};
```

扩展表不改检查器，`at` 对未知键抛 out_of_range；实际 UI 可把异常转换成错误结果。若规则还依赖内容类型、监护许可、日期等，不再是阈值表问题，可定义 `IAgeRule` 操作并让检查器依赖其契约，以不同实现处理不同规则；这是接口扩展方案，不需要在本目录展开设计模式。

图 48：共同 Client 只保留共同客户能力，RegisteredClient 才承诺提供邮箱，AnonymousClient 没有此操作契约。

Switch 依赖 Lamp 使开关受能耗接口和具体灯类型影响；分离接口能把依赖缩到开关实际使用的能力。Lamp 同时具两能力并不自动违反 SRP：若它只是设备门面委派两个能力，仍可合理；若内含复杂统计、计费和硬件控制，能耗分析应由独立对象承担。SRP 由变化理由判断，不能仅数方法。

原便笺还漏了更新 state，连续 toggle 可能重复做同一动作。单开关独占控制的简单实现可在成功执行后反转 state；若多开关或远程控制可改变灯状态，应让 Switchable 提供可靠查询或幂等 setState，由灯状态作为权威，不能让各 Switch 的本地缓存互相矛盾。

```cpp
struct Switchable {
    virtual ~Switchable() = default;
    virtual void on() = 0;
    virtual void off() = 0;
};
class Switch {
    Switchable& target_;
    bool state_ = false;
public:
    explicit Switch(Switchable& target) : target_(target) {}
    void toggle() { // 假设仅此开关控制，初始设备为 off
        if (state_) target_.off(); else target_.on();
        state_ = !state_; // 若调用抛异常则不会错误更新缓存
    }
};
```

![5g 改进答案](assert/pc-5g-after.svg)

图 52：Person 私有保存身份数据和 EmailAddress 值；EmailAddress 的受控构造确保它始终有效。

原 public email 可在验证后被任意赋为非法值，因此“有验证函数”不保证有效性不变量。Person 同时承担身份表示与邮箱规则，规则变化影响身份类。把邮箱语法验证封装到 EmailAddress，Person 只接受有效值，职责和状态保护都更清楚。它是按值成员，图上用组合表达此实例部件归属；相同字符串可以复制到不同人的 EmailAddress 值，不意味着共享同一个实体邮箱对象。

```cpp
#include <stdexcept>
#include <string>
#include <utility>
class EmailAddress {
    std::string value_;
public:
    explicit EmailAddress(std::string value) : value_(std::move(value)) {
        // 教学规则：恰有一个 @，两侧非空，不含空白。
        const auto at = value_.find('@');
        if (at == std::string::npos || at == 0 || at + 1 == value_.size() ||
            value_.find('@', at + 1) != std::string::npos ||
            value_.find_first_of(" \t\r\n") != std::string::npos)
            throw std::invalid_argument("invalid email under tutorial rule");
    }
    const std::string& text() const noexcept { return value_; }
};
class Person {
    std::string name_, firstname_;
    EmailAddress email_;
public:
    Person(std::string n, std::string f, EmailAddress e)
        : name_(std::move(n)), firstname_(std::move(f)), email_(std::move(e)) {}
    void changeEmail(EmailAddress value) { email_ = std::move(value); }
};
```

代码的验证规则是明确缩小的教学规则，**不等于完整互联网邮箱语法验证，也不证明地址可投递或属于此人**。生产系统可通过专门验证组件及发送验证邮件处理语法和所有权；本题的 UML 重点是让无效值无法直接绕过边界进入 Person，实际“有效”的定义必须由需求给出。
